## Hard operational rules

- **CI applies each stack in this repo on a merge to `main` that touches that stack's own inputs** (`.github/workflows/ci.yml`): the mail stack and both `hetzner/` stacks (`branchleft-hetzner-network`, then `branchleft-hetzner-estate`, serialised because the estate reads the network's outputs). A merge that changes only one stack's inputs — or none — plans and applies only that stack, or none at all; a `changes` job traces each program's actual import graph to a per-stack `paths:` filter, so a docs-only merge parks zero apply approvals. Do not hand-apply any of them — a hand `pulumi up` is first-time provisioning or a gated migration, never the steady state. Each apply is a plan job whose `pulumi preview` output lands in the job summary, then an apply job paused by the `production` environment's required-reviewer rule until a human has read that plan — the delete guard catches the destruction class mechanically; the reviewer catches the plan that is green and still wrong. The Hetzner stacks' delete guard is `scripts/assert-no-hetzner-deletes.py`; their bootstrap procedures are `mail/RUNBOOK-import-mail-host.md`, `hetzner/RUNBOOK-new-stack.md` and `hetzner/RUNBOOK-estate-project-move.md`.
- **No stack config file in this repo carries an `encryptionsalt`.** It is an offline verifier for the stack passphrase, so a public tree must not hold one. CI appends each stack's salt from its own repository secret at deploy; an operator appends it from their own copy only for a hand-gated stack operation, and never commits the result.
- `sites.ts` is the single hostname registry: `hetzner/edge/render.ts` derives the Caddy config and CrowdSec acquisition files from it, and `hetzner/monitoring/render.ts` derives blackbox probe targets from it. Read its own docstring before changing an entry.
