# status_page

This role delivers the status page of the estate: a Gatus container that probes every
hostname in the site registry once a minute and shows the result, with a history that
survives a restart. The page is served on loopback only. It is reached through an SSH
tunnel until a public route is chosen, and that route is not this role's work.

## What it does, and what it does not

It writes two Gatus configuration files and one Compose file into a project directory,
brings the stack up when the content it delivers is not the content last recorded as
healthy, and records the content only after the page answers `200` on `/health` from the
host itself. A run that fails part-way is followed by a run that tries again.

The stack has two services, both from the one pinned image. `gatus` is the page. The
`status-test-target` service is a second Gatus that answers `/health`, and the page probes
it as a component called TEST. Stopping it is the control case: a TEST incident opens
within about two probe intervals, and starting it again resolves the incident. Incidents
open and close from probe state alone, which is the rule in
`hetzner/monitoring/statusIncidents.ts`: Gatus records an event at the first changed
result, so no alert threshold is set.

It does not install Docker or the Compose plugin, publish the page on any address but
loopback, route a public hostname to it, send an alert, hold a secret, or remove a
volume. It runs no `down`, removes no orphan container and renews no anonymous volume. The
existing Prometheus and Alertmanager path stays the pager.

## Interface

[`meta/argument_specs.yml`](meta/argument_specs.yml) declares the variables and
[`defaults/main.yml`](defaults/main.yml) holds their defaults. There are two, and no secret:

- `status_page_listen_address`: `127.0.0.1` is the only value the specification allows. The
  role asserts it again, and also reads the Compose file as rendered and refuses any
  published port that does not start with `127.0.0.1:`, so the check holds if the
  specification is ever switched off.
- `status_page_wait_timeout`: seconds the stack may take to become healthy, used for the
  Compose wait and for the health check.

The image, the port (`8303`), the project directory (`/opt/branchleft/status`) and the
Compose project name are constants in [`vars/main.yml`](vars/main.yml), so a caller's
variable cannot move them. The image is Gatus v5.37.0, pinned by its index digest; the
image is a scratch image with no shell, so it cannot carry a Compose healthcheck, which is
why the health check runs from the host.

## Where its recipe comes from

The tasks are a copy of the `compose_stack` pattern's recipe in `ansible/patterns/compose_stack`
with this page's names, its template, its two configuration files and its endpoint check. A role
may not apply another role (ANS-12), so a change to the recipe is carried here by hand, and the
pattern's widened contract (named configuration files, the optional endpoint check) is what this
copy uses. The stamp covers the compose file and both configuration files with their modes, so
the first apply after a change to this copy brings the stack up once, recreating its two
containers; the `status-data` volume is kept.

## Requirements

The host has Docker with the Compose plugin, and the `community.docker` collection from the
pinned Ansible lock. The role creates no user or group; the files belong to root.

## What it changes on a host

- `/opt/branchleft/status/compose.yml`, checked by `docker compose config` on a temporary
  copy before it replaces the old one.
- `/opt/branchleft/status/stack/config.yaml` and `target.yaml`, copied from
  `hetzner/status/stack/` through the link `files/stack`. They are generated by
  `hetzner/status/render.ts` from `sites.ts`, so the hostname list has one home. Run
  `npm run render` in `hetzner/` after changing a hostname, and commit the result;
  `hetzner/status/render.test.ts` fails if the committed files drift.
- `/opt/branchleft/status/.status_page_stamp`, the digest of the content last brought up
  and found healthy, written last.
- The Compose project `status`: the page, the TEST target and the named volume
  `status-data`, which holds the page's history.

Both services run with a read-only root file system, every capability dropped,
`no-new-privileges`, a memory limit and `restart: unless-stopped`. Neither mounts the
Docker socket, and the only host files they mount are the configuration, read-only.

## How the stack is brought up

A bring-up is due when the stamp differs from the digest of the Compose file and the two
configuration files as the repository holds them, or when a delivery task changed a file in
this run. The second case covers a file edited by hand and put back, because a container
that bind-mounts a file keeps the inode it started with. The role then recreates the
containers, checks that every service in the Compose file is running, and asks
`/health` from the host, retrying until the wait timeout. Only a `200` writes the stamp.

## Run the test

From the repository root, with the tools installed as `ansible/README.md` describes:

```text
.venv/bin/python ansible/harness/run_harness.py ansible/roles/status_page
```

The test needs Docker, and the machine that runs it must not be a production host. The
scenario in `molecule/default/` replaces `docker` with a stand-in that records its calls and
runs no container, and replaces the page with a small web server that answers `/health`. It
proves the files, the arguments of every Compose call, that nothing removes data, the
refusal of a wide bind, a digest-less image and an override file, and that a page which does
not answer leaves no stamp. It does not prove that Gatus accepts the configuration or
probes anything; the first live apply does.

The listen-address refusal is the safety-class case. To see it red, remove the `choices` from
the specification and the first assert task from `tasks/main.yml`: the scenario then fails
because the role accepts `0.0.0.0`. With both restored it passes.

The renderer has its own test, run from `hetzner/` with `npm test`.

## How it is delivered

The role is listed in the playbook of the control-plane host, after the roles that bring
that host under the gated pull, and in `ansible/checks/host_roles.yml`. A merge to `main`
queues the gated apply, which waits for the owner's approval. After the apply, the page is
reached through an SSH tunnel to the loopback port, and the TEST target is stopped and
started once to see an incident open and resolve.

## How to change it safely

- A new hostname goes in `sites.ts`, then `npm run render` in `hetzner/`. Do not edit
  `hetzner/status/stack/` by hand.
- A new Gatus version is a new digest in `vars/main.yml`. Read the release notes for the
  configuration keys first, and read the first apply's result: Gatus rejecting the
  configuration shows up there and nowhere earlier.
- Do not add a published port, a bind other than loopback, a volume that is a host path,
  or an alerting block without changing the argument specification, the assert and the
  scenario together.
- Publishing the page on a public hostname is a separate change: it needs a registry entry,
  DNS, a certificate and a firewall rule for the port.
