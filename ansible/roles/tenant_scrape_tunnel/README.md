# tenant_scrape_tunnel

Lets Prometheus on `edge1` read the node exporters of the three tenant hosts (`db-t1`, `app-t1` and
`edge-t`, port 9100) over one SSH connection that `edge1` opens to `edge-t`. The tenants network is a
separate network, so `edge1` cannot reach those exporters directly. The connection uses a key and an
account that exist for this purpose only, and `edge-t`'s sshd lets that key forward to the three
exporter ports and do nothing else.

One role, two halves, chosen by the host's name in the play (`enrolled_host`):

| Host    | Half               | What it does                                                                                                  |
| ------- | ------------------ | ------------------------------------------------------------------------------------------------------------- |
| `edge1` | `tasks/_edge1.yml` | Makes the tunnel account and key, prints the public half, and (once data is in) installs and starts the unit. |
| `edget` | `tasks/_edget.yml` | Prints its own SSH host public key, and (once data is in) installs the restricted key and the sshd drop-in.   |

Any other host name stops the run with `TENANT_SCRAPE_TUNNEL_HOST_NOT_ENROLLED`.

This role does **not**: scrape anything (the Prometheus configuration is generated by
`hetzner/monitoring/`), open a path to the `db-t1` database or to any port other than the node
exporters, give any person or pipeline a login on `edge-t`, or touch the other accounts and keys on
either host (`ci_jump`, `ci_login`, `tunnel_account`).

## Interface

`meta/argument_specs.yml` documents the three inputs, all in `defaults/main.yml`. All three are public
data, none is a secret, and each is empty until the data commit below fills it in. **Empty means off.**

| Variable                                  | Read by | What it is                                                           |
| ----------------------------------------- | ------- | -------------------------------------------------------------------- |
| `tenant_scrape_tunnel_scraper_public_key` | `edget` | `edge1`'s tunnel public key (one `ssh-ed25519` line).                |
| `tenant_scrape_tunnel_target_host_key`    | `edge1` | `edge-t`'s SSH host public key (one `ssh-ed25519` line).             |
| `tenant_scrape_tunnel_target_endpoint`    | `edge1` | The DNS name or IPv4 address `edge1` connects to (no port, no user). |

Everything else is a constant in `vars/main.yml`, which outranks any caller's variable: the account,
every path, the unit's name, the three destinations (name, address, local port), the target port, the
bind address, and the unit file's sha256. A plain `role:` entry with no variables is the only way the
role is wired (`check_enrolment` R2).

## Requirements

- `edge1`: OpenSSH client (`/usr/bin/ssh`), systemd, and either `ssh-keygen` or the Python
  `cryptography` library for `community.crypto.openssh_keypair`. The role gathers the network facts it
  needs itself, so the play may run with `gather_facts: false`.
- `edget`: the OpenSSH server with its `sshd_config.d` directory (the role stops if it is missing).

## Turning the tunnel on

Nothing is copied by a person, and no key, host key or address is in this repository until a reviewed
commit puts it there. The order, with the apply being the gated pull of `main` on each host:

1. **First apply (code merged, defaults empty).**
   - `edge1` creates the account `scrapetunnel` (no login shell) and its ed25519 key (never
     regenerated), and prints one line starting `tenant_scrape_tunnel scraper_public_key: ` followed by
     the public key. It installs no unit.
   - `edget` prints one line starting `tenant_scrape_tunnel target_host_key: ` followed by its
     `/etc/ssh/ssh_host_ed25519_key.pub`. It creates nothing.
   - Each half also prints a `tenant_scrape_tunnel waiting:` line while its data is missing.
2. **Data commit (an agent step, then the owner's review).** An agent reads the first apply's log,
   takes the two lines above (public data only: the private key is never read, printed or logged) and
   the `edge-t` endpoint it is given, and opens a commit that fills the three defaults in
   `defaults/main.yml`. This directory is owner-owned in `CODEOWNERS`, so the owner reviews and merges
   it. The role refuses a value that is not one `ssh-ed25519` line (keys) or not a DNS name or IPv4
   address (endpoint), and says which.
3. **Second apply (defaults filled).**
   - `edget` creates the account with no login shell, writes the restricted authorized key and the
     sshd drop-in, checks the whole sshd configuration, reloads sshd, and reads the effective
     settings back. A failed check or read-back puts the previous files back and fails the run
     (`TENANT_SCRAPE_TUNNEL_SSHD_REFUSED`).
   - `edge1` pins the host key in a `known_hosts` file, writes the target file, installs the unit,
     and starts it, or restarts it when one of its files changed.
4. **Retries.** `edge1`'s unit has `Restart=always` with a growing delay, so it keeps trying until
   `edget` has the key. The two applies may land in either order. If the key on `edge1` was ever
   replaced, the unit retries without end and Prometheus shows the targets down: the data commit must
   be redone from a new first-apply log.

Feature off and the plan: with all three defaults empty each half only reports and nothing else
changes, so the plan of a host shows no change beyond the account, the key directory and the key.

## What it changes on a host

`edge1`: the account `scrapetunnel`; `/etc/branchleft/tenant-scrape/` (root, 0755) holding the private
key (the account's, 0600) and its public half, and, once data is in, `known_hosts` (root, group the
account, 0640), `target.env` (root, 0600, the endpoint only) and the unit
`/etc/systemd/system/branchleft-tenant-scrape.service`.

`edget`, once data is in: the account `scrapetunnel`, `/etc/ssh/branchleft-tenant-scrape/authorized_keys`
(root, 0644, exactly one line) and `/etc/ssh/sshd_config.d/50-branchleft-tenant-scrape.conf`.

No path is made from the account's name.

## Threat model

- **The key can do one thing.** Its `authorized_keys` line is `restrict,port-forwarding`, one
  `permitopen` for each of the three exporter address:port pairs, and `command="/usr/sbin/nologin"`,
  then the key type and body, and nothing else. sshd's own `Match User` block for the account repeats
  it: `AuthenticationMethods publickey`, `AllowTcpForwarding local` (so a remote forward is refused),
  the same `PermitOpen`, `PermitListen none`, and agent, X11, stream-local, tty, tunnel and user-rc
  all off, `ForceCommand /usr/sbin/nologin`. Both files are made from the one `destinations` list in
  `vars/main.yml`, so they cannot differ.
- **No shell, no password.** The account's shell is `/usr/sbin/nologin`; the role refuses to adopt an
  existing account that has a login shell.
- **The private key never leaves `edge1`.** It is made there by the key module with `no_log` and
  `diff: false`, is never read, slurped, printed or put in a fact, and is owned by the unit's own user.
  Only the public half is read, with `no_log`, and printed once; that one `debug` cannot be `no_log`
  because it exists to show public data.
- **`edge1` checks `edge-t`.** The unit uses `StrictHostKeyChecking=yes`, `HostKeyAlias`, its own
  `known_hosts` file, `GlobalKnownHostsFile=/dev/null` and `UpdateHostKeys=no`. The host key comes from
  the reviewed data commit, never from `ssh-keyscan` or trust on first use.
- **The unit opens exactly the three forwards.** Three `-L` options, each bound to `edge1`'s private
  address explicitly (never `0.0.0.0`), and no `-R`, `-D`, `-W` or `-g`. `ExitOnForwardFailure=yes`.
  The role holds the unit's text to the constants, refuses any other single-letter option, and holds
  the file to its pinned sha256 (a tripwire against an accidental edit, not a control on a deliberate
  one). It also refuses to start unless `edge1` holds the bind address.
- **No value in a log.** The endpoint and the pinned key are written by tasks with `no_log` and
  `diff: false`. The unit's hardening is the same set as `tunnel_account`'s database tunnel: no new
  privileges, strict filesystem, no devices, no capabilities.
- **Not covered:** the `db-t1` database exporter. Only the three node exporters are reachable; a
  database exporter would be a fourth destination and a reviewed change to `destinations`. The
  address-conditional `Match` blocks of other sshd files are not seen by the read-back, which asks
  sshd about the loopback address. Whether the Prometheus container can reach a host-bound listener
  on `edge1`'s host firewall is proven by the first live scrape, not here.

## Tests

- `python3 ansible/checks/run_role_unit_tests.py ansible` runs `tests/unit/`, which renders the real
  templates and parses the real unit file.
- `ansible/checks/test_tenant_scrape_tunnel_pins.py` holds the addresses, ports and bind address
  equal to the address plan and the Prometheus configuration's generator.
- `molecule test` in this directory runs both halves in a container against a real sshd. It needs a
  container engine, so it is proven in CI.

## Delivery

Delivered only by the gated pull (`ANS-17`): merge to `main`, then the plan, the owner's approval and
the host's own apply. Nothing in this role is applied by hand.

## Changing it safely

- A new destination is one entry in `destinations`, a new local port in the unit file, the new
  `-L`, the new sha256 in `vars/main.yml` and the matching target in `hetzner/monitoring/`. The
  pins test fails until they agree.
- The unit file's sha256 is `sha256sum files/branchleft-tenant-scrape.service`.
- Never loosen the key options, the drop-in or the unit's asserts to make a check pass; a wider
  forward is a design change for the owner.
- To rotate the key, remove the private and public key files on `edge1`, then repeat "Turning the
  tunnel on" from step 1.
